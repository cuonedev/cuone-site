　　本机开发会同时用到 Codex 和 OpenCode。一个环节完成后，另一个工具里的 Agent 不会自动收到前面的背景和结论，任务信息只能先写进 Markdown，再由人转交。和同事协作时也有类似情况：各自的 Agent 都能完成工作，彼此却没有直接沟通的渠道。

![多个 Agent 分担开发环节，但目前仍由 Markdown 和人工完成交接]({{ '/assets/images/posts/01-agent分工与人工交接.png' | relative_url }})

## 多模型与多工具的选择

　　开发任务有不同类型。方案分析、代码实现、审查和资料检索，对模型能力的要求并不一样，成本也有差异。按任务选择模型，可以让不同模型承担更合适的工作，也能控制整体成本。

　　工具选择也有类似考虑。不同 Agent 的交互方式、模型接入范围和子 Agent 能力各不相同，继续使用多种工具，可以保留各自擅长的部分，也符合现有工作习惯。

　　因此，开发流程里自然形成了多个模型、多种 Agent 协同分工的局面。分工可以运转，问题出在交接：Agent 之间没有共同的沟通方式。

## 人工交接的协作断点

　　目前，Markdown 主要承担任务背景和阶段结论的交接。分析完成后，需要把方案和注意事项整理下来，交给负责编码的 Agent；代码完成后，审查意见也要由人转交给后续环节。

　　这种方式简单可靠，也留下了记录。但每次交接都要有人整理内容、找到接收方，再确认后续进度。文档不会主动通知对方，也无法说明消息是否收到、任务是否接手。要了解进展，仍要靠人工追问和更新。

　　与同事协作时，交接还要跨越不同人的开发环境。每个人都能让自己的 Agent 工作，但 Agent 之间没有共同的沟通渠道，信息依然要由人阅读、转述，再催促接手。

　　所以，当前缺少的不是更多 Agent，而是让不同 Agent 能够交换任务信息，并让人看清交接进度的协作方式。

![人工整理 Markdown 交接与协作服务传递 Agent 消息的对照]({{ '/assets/images/posts/02-人工交接与消息协作.png' | relative_url }})

## 社区的几种尝试

　　顺着这个问题找下去，会发现社区里的探索并不只有一种。大致可以看到几条路线：

　　这些路线涉及协议、工具内部能力、会话中继和独立服务等不同层次。MCP（Model Context Protocol，模型上下文协议）是 AI 应用连接外部工具与服务的一种协议入口。

- **Agent 间通信协议。** [A2A（Agent2Agent）](https://github.com/a2aproject/A2A) 希望不同 Agent 系统遵循共同协议进行互通。它提供的是协议规范，现有开发工具还需要实现协议或提供适配。
- **Agent 自带的团队功能。** 一些编码工具可以在自己的产品内部创建子 Agent、分配任务。这种方式用起来直接，但团队成员通常受限于同一套工具。
- **终端或本地会话中继。** [WezTerm Chat MCP](https://github.com/yangzy7513/wezterm-chat-mcp) 借助 WezTerm 窗格在不同会话间传递消息；[Modula Relay](https://github.com/modulastack/modula-relay) 使用本地 Unix socket 连接 Agent。它们依赖特定终端或本机进程模型，是否适用于跨设备协作要分别核对网络与部署能力。
- **独立的 Agent 通信服务。** [cross-agent-teams-mcp](https://github.com/jtianling/cross-agent-teams-mcp) 等项目可作为调研案例。各项目的工具支持、部署方式和消息接收能力需要分别依据项目说明与实际验证确认。

　　其中不少项目也使用 MCP 作为接入方式。消息路由、广播、任务协作等则由具体服务实现。项目使用 MCP，并不意味着它们提供相同的协作能力。

## 当前场景需要什么

　　结合这些路线，当前场景需要的协作方式逐渐清晰：不同工具、不同开发环境中的 Agent 能够互通；分析结论可以交给指定的编码 Agent，任务进展可以同步给相关成员，交接记录也能回看。Codex、OpenCode 等工具则继续按原来的方式使用，不必为了协作迁移到同一套产品。

　　换句话说，目标是**Agent 尽量少改，使用者尽量少配**。连接服务、标识 Agent、设置必要权限仍然需要；后续方案可通过安装向导、自动生成配置和合理默认值，减少使用者逐个工具手工配置的负担。

## 为什么优先验证 MCP 接入

　　MCP 提供了 AI 应用连接外部工具与服务的接入方式，因此值得优先验证它能否覆盖当前使用的不同开发工具。实际可用能力取决于工具版本和实现，需要在当前环境中逐项测试。

　　在待验证的方案中，Agent 通过 MCP 调用协作服务；协作服务负责身份管理、消息路由和协作记录等业务能力。这些是服务端需要实现的职责，不是 MCP 自动提供的功能，也不代表当前已经有对应实现。若接入验证顺利，这种分工有望复用不同工具已有的接入能力，减少为每种工具单独开发通信机制的需要。

　　不过，消息发出后能否及时送达并唤起接收方，还要看具体实现。有的 Agent 需要主动查看收件箱，有的项目会针对特定宿主增加唤醒适配。仅接入 MCP，并不保证接收方会自动响应。后续还需比较各项目的消息接收和唤醒方式，看看它们能否适用于本机多工具与同事跨环境协作。

![待验证方案：MCP 接入与协作服务的职责分工，消息唤醒仍取决于宿主能力]({{ '/assets/images/posts/03-MCP接入与消息流转.png' | relative_url }})

　　接下来，我会先用社区已有的 MCP 项目，在本机验证不同 Agent 能否完成消息发送、接收和交接，并重点观察接收方如何获知新消息。跑通这条协作链路后，再结合实际使用中暴露出的差距，判断哪些能力需要补齐，以及是否需要将协作服务单独工程化。它与轻量通用 Agent 项目 `cuo-agent` 的职责边界，也会在方案明确后再说明。
